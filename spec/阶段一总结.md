# Echoes 阶段一代码审查总结

## 审查范围
- 已审查：`src/`、`scripts/notify.py`、`.github/workflows/deploy-oss.yml`、`src/config/site.config.yaml`
- 已排除：`spec/极简主义原型图-v2.html`（按你的要求不纳入）
- 审查时间：2026-02-14

## 总体结论
- 框架混用没有失控，但“交互复杂度”和“实现方式”不均衡：`archive` 用 React 可接受，`index`/`TOC` 仍是较重的命令式 DOM 脚本，维护成本偏高。
- 状态管理存在割裂：全局 store（`nanostores`）与页面局部状态并存，但缺少统一状态源，URL 状态与 UI 状态不同步。
- 配置系统存在结构性风险：配置读取是同步 I/O 且反复执行，类型定义与 YAML 已漂移，缺少运行时校验。

## 关键问题（按严重级别）

### P0（高）
1. 归档筛选状态未回写 URL，导致刷新/分享/回退行为不一致
- 位置：`src/components/archive/ArchiveApp.tsx:30`、`src/components/archive/ArchiveApp.tsx:49`、`src/components/archive/ArchiveApp.tsx:247`、`src/components/archive/ArchiveApp.tsx:260`
- 现象：组件会从 URL 初始化和监听 `popstate`，但用户点击分类/标签后只改本地 state，不更新地址栏。
- 影响：筛选结果不可分享；刷新后状态丢失；浏览器历史与当前 UI 不一致。
- 建议：新增统一 `syncFiltersToUrl()`，在 `activeCategory`/`activeTags` 变化时 `history.replaceState`（或 `pushState`）同步。

2. 配置读取为“每次调用同步读文件”，且在循环中被频繁触发
- 位置：`src/lib/config.ts:70`、`src/lib/config.ts:72`、`src/lib/utils.ts:25`、`src/lib/utils.ts:37`、`src/pages/archive.astro:29`、`src/components/home/TimelineItem.astro:16`
- 现象：`getSiteConfig()` 每次调用 `readFileSync`；`getCategoryColor/getCategoryLabel` 又在文章遍历中反复调用。
- 影响：构建期和 SSR 路径存在不必要 I/O；随着文章增多会明显放大；未来切换到按请求渲染时风险更高。
- 建议：模块级缓存配置（开发模式按文件时间戳失效），并将分类映射一次性注入，避免循环内读配置。

### P1（中）
3. 交互复杂但仍是命令式 DOM 脚本，生命周期分散、可维护性弱
- 位置：`src/pages/index.astro:87`、`src/pages/index.astro:131`、`src/pages/index.astro:150`、`src/components/post/TableOfContents.astro:47`、`src/components/post/TableOfContents.astro:99`、`src/components/post/TableOfContents.astro:127`
- 现象：时间线加载与 TOC 高亮都靠手写查询/监听/DOM 变更；逻辑分散在页面脚本，复用和测试困难。
- 影响：后续需求（键盘导航、无障碍、动画策略、埋点）会不断推高维护成本。
- 建议：二选一：
- 方向 A：抽成小型岛组件（React/Preact 皆可），用组件状态管理事件生命周期。
- 方向 B：继续 Astro 原生脚本，但抽独立模块并引入显式 `init/destroy` 约定。

4. 配置类型定义与 YAML 已漂移，缺少运行时校验
- 位置：`src/lib/config.ts:59`、`src/lib/config.ts:63`、`src/config/site.config.yaml:70`、`src/config/site.config.yaml:74`
- 现象：TypeScript 接口声明了 `deviceKeyEnv`，YAML 中没有；YAML 有 `templates`，接口中未声明；读取后直接 `as SiteConfig` 强转。
- 影响：类型系统无法兜底配置错误，线上只会在运行时暴露。
- 建议：对 `site.config.yaml` 引入 `zod`（或同类）运行时 schema 校验，禁止裸 `as`。

5. CI 通知脚本自写 YAML 解析器，抗变更能力弱
- 位置：`scripts/notify.py:21`、`scripts/notify.py:23`、`scripts/notify.py:32`
- 现象：解析器明确跳过数组行（`- `），只覆盖“当前可用子集”。
- 影响：一旦通知模板结构稍改（列表、嵌套变复杂），脚本将静默误解析。
- 建议：改为标准 YAML 解析（允许增加依赖），或将通知模板独立为 JSON 并做 schema 校验。

6. 标签归一化策略分散，筛选阶段重复计算
- 位置：`src/pages/archive.astro:40`、`src/components/archive/ArchiveApp.tsx:84`
- 现象：文章 tags 在服务端未统一规范，客户端每次过滤都做 `toLowerCase()` + `map()`。
- 影响：数据规模变大时有额外开销，也增加了大小写边界行为的不确定性。
- 建议：在序列化阶段增加 `tagsNormalized`，筛选时直接使用。

### P2（低）
7. 存在未落地/未使用状态，增加认知负担
- 位置：`src/stores/player.ts:10`、`src/stores/player.ts:13`
- 现象：播放器 store 在仓库中仅定义未使用（当前阶段无消费方）。
- 影响：读代码时会误判为“已有播放器能力”，增加维护噪音。
- 建议：未启用功能移入 feature flag 目录或明确标注 `phase-2`。

8. 遗留 DOM 节点未使用
- 位置：`src/layouts/BaseLayout.astro:72`
- 现象：`#dynamic-bg` 目前无任何脚本或样式消费。
- 影响：语义噪音；后续定位样式问题时增加排查成本。
- 建议：删除或补齐用途注释与实现。

9. Header 存在可疑样式类名
- 位置：`src/components/common/Header.astro:35`
- 现象：类串包含独立的 `/70` token（看起来是残留编辑结果）。
- 影响：可读性差，且可能掩盖本应存在的背景透明度类。
- 建议：清理无效 class，并明确背景层实现策略。

## React / Astro 边界评估
- `src/pages/archive.astro:78` 仅此页使用 `React + client:load`，用于分类/标签/关键词复合筛选，方向总体合理。
- 但首页时间线与文章 TOC 已具备“中高交互复杂度”，继续使用命令式脚本会越来越不优雅；建议阶段二优先组件化这两处。
- 当前项目不存在“到处滥用 React”的问题，主要矛盾是“复杂交互未组件化”。

## 状态管理评估
- 全局主题：`src/stores/theme.ts` 可用，但以命令式函数为主，`$isDark` 当前未被消费，store 价值未完全体现。
- 归档筛选：完全局部 state，缺少与 URL 的单一数据源同步（这是最需要先修的状态问题）。
- 播放器状态：`src/stores/player.ts` 仍处于预埋状态，建议收敛到明确阶段再开放。

## 隐藏改进点（阶段一可落地）
1. 修正归档 URL 同步（先做）
2. 给 `getSiteConfig` 加缓存与 schema 校验（先做）
3. 把 `index` 时间线脚本抽为独立模块并补 `destroy`（次优先）
4. TOC 改为 IntersectionObserver 方案，减少滚动计算（次优先）
5. 清理未使用 store/DOM 节点与可疑 class（快速收益）

## 建议的阶段一执行顺序
1. 功能一致性：修复归档筛选 URL 状态同步
2. 架构稳定性：配置缓存 + 运行时 schema 校验
3. 可维护性：时间线与 TOC 交互模块化
4. 噪音清理：未使用代码和样式残留清理
